Chapter 09

Async with tokio

Tokio gives Rust the goroutine-shaped mental model you already have — lightweight tasks, a scheduler, non-blocking I/O — but the machinery is opt-in and visible rather than built into the runtime, and that visibility is exactly what caused (and eventually explained) the most instructive bug in this crate's history.

The mental model

An async fn doesn't run when called — calling it produces a state machine (a value implementing Future) that does nothing until something polls it, typically via .await. A tokio runtime is what actually polls futures to completion, scheduling many of them across a thread pool. Tasks (spawned with tokio::spawn) are tokio's rough equivalent of goroutines — cheap, many-per-thread, scheduled by the runtime rather than the OS — but they're cooperatively scheduled at .await points, not preemptible the way Go's runtime can interrupt a goroutine between almost any two instructions. A task that never awaits never yields.

main.rs builds a small multi-thread runtime explicitly, rather than using the #[tokio::main] macro that hides this:

lb/src/main.rs — main
let runtime = match tokio::runtime::Builder::new_multi_thread()
    .worker_threads(2)
    .enable_all()
    .build()
{
    Ok(rt) => rt,
    Err(e) => {
        eprintln!("quixiot-lb: failed to start runtime: {e}");
        return ExitCode::FAILURE;
    }
};

Two worker threads, every tokio feature enabled (timers, I/O, signals), then block_on drives the top-level serve(cfg) future to completion on this runtime — the one place the whole async machinery is entered from synchronous main. The comment explains the worker count choice: this workload is I/O-bound, so a couple of workers keep the receive loop and return tasks moving without oversubscribing the machine with more OS threads than there's parallel work to do.

Spawning tasks

tokio::spawn hands a future to the runtime and returns immediately with a JoinHandle; the task runs independently, detached from the spawner unless you explicitly await or abort the handle. This crate spawns three kinds of long-running task: one return task per session,

tokio::spawn(Arc::clone(self).return_loop(Arc::clone(&session)));

the idle sweeper,

let sweeper = tokio::spawn(Arc::clone(&self).sweep_loop());

and one health-probe loop per backend:

tokio::spawn(probe_loop(config, backend));

The sweeper is also the one task this crate cancels explicitly rather than letting run forever: when the accept loop exits (shutdown), it calls abort() on the sweeper's handle to stop it immediately rather than waiting for its next tick:

sweeper.abort();

select!: whichever completes first

tokio::select! polls several futures concurrently and proceeds with whichever resolves first, dropping the others' partially-completed state. The accept loop races a shutdown signal against the next incoming datagram:

lb/src/balancer.rs — Balancer::run
loop {
    let recv = self.listen.recv_from(&mut buf);
    let (n, client) = tokio::select! {
        _ = shutdown.notified() => {
            info!("shutdown requested; stopping accept loop");
            break;
        }
        result = recv => match result {
            Ok(pair) => pair,
            Err(e) => {
                error!("recv_from on listen socket failed: {e}");
                break;
            }
        },
    };

and every session's return task races the same shutdown signal against the next reply from that session's upstream socket:

lb/src/balancer.rs — Balancer::return_loop
    tokio::select! {
        _ = session.shutdown.notified() => break,
        result = session.upstream.recv(&mut buf) => match result {
            Ok(n) => {
                session.touch();
                self.metrics.add_to_client(n);
                // Same drop-not-block rationale as the accept loop: the
                // listen socket is shared by every session's return
                // task, so nobody gets to park on it.
                match self.listen.try_send_to(&buf[..n], session.client) {
                    Ok(_) => {}
                    Err(e) if e.kind() == ErrorKind::WouldBlock => {
                        self.metrics.drop_to_client()
                    }
                    Err(e) => {
                        warn!("send to client {} failed: {e}", session.client);
                        break;
                    }
                }
            }
            Err(e) => {
                self.handle_upstream_error(&session, e, "recv from upstream");
                break;
            }
        },
    }
}

Cancellation safety in one paragraph: when select! picks a winner, the losing branch's future is simply dropped mid-poll. For a plain .notified() or .recv_from() call, that's safe — there's no partial side effect to worry about, the operation just didn't happen. It's a real design constraint you'd need to think about with more stateful futures (a half-completed multi-step operation), but every select! in this crate races futures that are safe to abandon this way.

Go contrast

Go's netpoller blocks a goroutine on a channel or a network read transparently — the scheduler parks it and resumes it later, and you never see the readiness machinery underneath. Rust's futures make that machinery an explicit, visible layer: select! is you naming exactly which operations are racing, and (as the war story below shows) the readiness state each socket carries is something you can occasionally observe directly rather than never at all.

Notify: permit semantics

tokio::sync::Notify is a minimal wake-up signal, simpler than a channel: no payload, just "something happened, wake up." Its useful subtlety is that notify_one() stores a permit if nobody is currently waiting, so a signal sent between two poll iterations of the waiter's loop isn't lost — a plain condition-variable-style signal can drop a wakeup that arrives in that gap. The comment in spawn_signal_handler states this directly:

lb/src/main.rs — spawn_signal_handler
fn spawn_signal_handler(shutdown: Arc<Notify>) {
    tokio::spawn(async move {
        #[cfg(unix)]
        {
            use tokio::signal::unix::{signal, SignalKind};
            let mut term = match signal(SignalKind::terminate()) {
                Ok(s) => s,
                Err(e) => {
                    warn!("cannot install SIGTERM handler: {e}");
                    return;
                }
            };
            tokio::select! {
                _ = tokio::signal::ctrl_c() => info!("received Ctrl-C"),
                _ = term.recv() => info!("received SIGTERM"),
            }
        }
        #[cfg(not(unix))]
        {
            let _ = tokio::signal::ctrl_c().await;
            info!("received Ctrl-C");
        }
        // notify_one stores a permit if the accept loop isn't parked in select
        // at this instant, so the shutdown can't be missed between iterations.
        shutdown.notify_one();
    });
}

Ctrl-C or SIGTERM (on Unix, raced against each other with their own inner select!) calls shutdown.notify_one() exactly once; whichever of the accept loop's future iterations is either already waiting on shutdown.notified() or gets there microseconds later, the permit guarantees it wakes.

tokio::time: timeout and interval

tokio::time::timeout wraps any future with a deadline, turning "no reply in N milliseconds" into an ordinary Result branch instead of a callback or a second watcher task. The active health checker uses it directly:

lb/src/health.rs — probe_once
async fn probe_once(sock: &UdpSocket, timeout: Duration) -> Result<(), String> {
    // Drain anything already queued (e.g. a late reply to the *previous*
    // probe), so a stale packet can't be credited to this round. try_recv
    // returns WouldBlock once empty; any other error will resurface below.
    let mut buf = [0u8; 2048];
    while sock.try_recv(&mut buf).is_ok() {}

    let packet = build_probe();
    sock.send(&packet).await.map_err(|e| format!("send: {e}"))?;

    match time::timeout(timeout, sock.recv(&mut buf)).await {
        Ok(Ok(_n)) => Ok(()),                    // any reply -> alive
        Ok(Err(e)) => Err(format!("recv: {e}")), // e.g. ECONNREFUSED -> dead
        Err(_) => Err("timeout".into()),
    }
}

interval plus MissedTickBehavior::Skip is the periodic-timer pattern: if a tick is missed (a slow probe delaying the next one), skip straight to the next scheduled tick instead of firing a burst of catch-up ticks back to back:

lb/src/health.rs — probe_loop
async fn probe_loop(config: Arc<Config>, backend: Arc<Backend>) {
    let mut ticker = time::interval(config.health_interval);
    // If a tick is missed (e.g. a slow probe), skip it rather than firing a burst.
    ticker.set_missed_tick_behavior(time::MissedTickBehavior::Skip);
War story: the try_send readiness bug (the centerpiece)

This is the bug that most directly justifies this chapter existing. It happened in roughly this order.

1. The change. The hot forwarding path was switched from send().await to try_send, on purpose: this loop serves every client, so it must never park waiting on one session's socket buffer. A full buffer should drop that one datagram (safe under UDP/QUIC semantics; the client retransmits) and move on — drop-not-block, not stall-everyone.

2. The failure. New integration tests spinning up real UDP echo backends failed on every run — specifically, the first packet of every new session vanished. The test assertion read (from the test helper's .expect("reply within 2s")):

panicked at 'reply within 2s: Elapsed(())'

3. The diagnosis. Tokio's try_* methods (try_send, try_send_to) don't ask the OS “is this socket writable right now” on every call — that would defeat the point of being non-blocking. They consult the reactor's cached readiness state. A freshly registered socket hasn't yet observed its first writable-ready event from the OS, so that cached state starts out not-ready, and the very first try_send on a brand-new socket spuriously reports WouldBlock — even though the socket's send buffer is, in reality, completely empty and ready. The datagram that opened the session got silently dropped by the code that correctly treats WouldBlock as “drop and count it”.

4. The fix. Prime each socket's write readiness once, explicitly, with writable().await before the first real try_send — at both call sites where a fresh socket enters service:

lb/src/balancer.rs — Balancer::run
pub async fn run(self: Arc<Self>, shutdown: Arc<Notify>) {
    // Prime the listen socket's write readiness so the return tasks'
    // try_send_to doesn't spuriously drop the first replies (see
    // dial_upstream for the full story).
    if let Err(e) = self.listen.writable().await {
        error!("listen socket is unusable for writes: {e}");
        return;
    }
    let sweeper = tokio::spawn(Arc::clone(&self).sweep_loop());
lb/src/balancer.rs — Balancer::dial_upstream
async fn dial_upstream(&self, backend: &Backend) -> std::io::Result<UdpSocket> {
    // Sized kernel buffers (like the Go proxy's 8 MiB) so return-path
    // bursts from the backend aren't dropped at the socket before we can
    // read them.
    let (sock, _granted) = net::bind_udp(net::wildcard_for(backend.addr()), net::BUFFER_BYTES)?;
    sock.connect(backend.addr()).await?;
    // Prime write readiness once. tokio's try_send consults the reactor's
    // *cached* readiness, and a freshly registered socket hasn't seen its
    // first writable event yet — without this await the session's first
    // try_send spuriously reports WouldBlock and we'd drop the packet.
    // After priming, WouldBlock from try_send means "buffer really full".
    sock.writable().await?;
    Ok(sock)
}

5. The morals. Async runtimes have observable internals — “non-blocking” doesn't mean “stateless,” and a cached-readiness optimization can leak into observable behavior at exactly the boundary (a fresh socket's very first send) where you'd least expect it. And live QUIC traffic had never surfaced this in manual testing, precisely because real QUIC clients retransmit an unanswered Initial packet — the bug was silently self-healing under real traffic and only visible under a test harness with a bounded timeout and no retransmission to paper over the drop. Tests catching what demos mask is the whole reason chapter 11 exists.

Try it

In lb/src/balancer.rs, comment out the sock.writable().await?; line inside dial_upstream and run cargo test in lb/. Watch sticky_sessions_and_round_robin_distribution and recovered_backend_receives_new_sessions fail with reply within 2s: Elapsed(()) — on this machine the race loses every time, though readiness-caching bugs can be timing-sensitive elsewhere. Then restore the line and confirm the suite is green again. This is war story #4, reproduced by your own hands instead of read about.
