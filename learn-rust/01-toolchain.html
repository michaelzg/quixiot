Chapter 01

Cargo and the anatomy of a crate

Cargo is Rust's build tool, package manager, and test runner in one binary — think go build + go mod + go test collapsed into a single command with a project-wide manifest, rather than three tools that happen to agree with each other.

rustup, cargo, rustc

rustup installs and switches Rust toolchains (stable/beta/nightly, cross-targets) — the analogue of managing multiple Go versions with g or goenv, except it's the official, universally-used tool. cargo is what you actually type day to day: it resolves dependencies, invokes the compiler, runs tests, and formats and lints code. rustc is the compiler itself; you will rarely invoke it directly, the same way you rarely call the Go compiler binary instead of go build.

The commands you'll use constantly:

  • cargo build — compile (debug profile: fast to compile, unoptimized).
  • cargo run — build and run the binary target.
  • cargo test — compile and run every #[test] function (chapter 11).
  • cargo clippy — a much stricter linter than the compiler's own warnings (chapter 11).
  • cargo fmt — canonical formatting, no configuration debates (chapter 11).
  • cargo build --release / cargo run --release — build with optimizations on, using the [profile.release] settings below. Debug builds are for iterating; you'd never ship one.

This repo wraps the common cases: make lb builds the crate, make lb-test runs its test suite, make lb-demo runs a full three-backend scenario against a real build.

Anatomy of lb/Cargo.toml

Every crate (Rust's word for "package" — a compilation unit with its own Cargo.toml) declares itself in a manifest. Here is the whole file:

lb/Cargo.toml
[package]
name = "quixiot-lb"
version = "0.1.0"
edition = "2021"
rust-version = "1.75"
description = "An educational L4 UDP load balancer that fronts the QuixIoT QUIC/HTTP3 servers."
license = "MIT"
publish = false

[[bin]]
name = "quixiot-lb"
path = "src/main.rs"

# Two external dependencies, both deliberate:
#   tokio   — the async runtime and sockets.
#   socket2 — SO_RCVBUF/SO_SNDBUF sizing, which std does not expose. The Go
#             proxy sets 8 MiB buffers and this repo measures drop rates, so
#             matching matters for fair comparisons.
# Everything else — the strategy math, the RNG, the FNV hash, the Prometheus
# text exposition, the QUIC header parse — is hand-rolled in std so the crate
# stays small and the Rust concepts stay in view. See README.md.
[dependencies]
tokio = { version = "1", features = [
    "rt-multi-thread",
    "net",
    "time",
    "sync",
    "macros",
    "signal",
    "io-util",
] }
socket2 = "0.6"

[profile.release]
opt-level = 3
lto = "thin"

[package] names the crate and pins an edition — a Rust-version-independent opt-in to language changes (2021 here), plus a rust-version floor the crate promises to compile with. [[bin]] declares a binary target explicitly: name and entry-point path. (A lib.rs would declare a library target instead; a crate can have one library and many binaries.)

[dependencies] lists exactly two external crates, and the comment above them explains why each earns its place: tokio for the async runtime and sockets, with an explicit feature flag list — rt-multi-thread, net, time, sync, macros, signal, io-util — so the build only compiles the parts of tokio this binary actually uses, rather than the whole runtime. socket2 exists for exactly one thing std doesn't expose: setting SO_RCVBUF/SO_SNDBUF buffer sizes (see chapter 3). Everything else in this crate — the load-balancing math, the RNG, the FNV hash, the Prometheus text format, the QUIC header parser — is hand-rolled against the standard library. That's a deliberate choice to keep the Rust concepts in view instead of buried inside a dependency.

version = "1" for tokio is a caret requirement: it means "≥1.0.0, <2.0.0" — any semver-compatible 1.x release. Cargo resolves the newest version matching every dependency's constraints and records the exact versions it picked in Cargo.lock. For a binary crate like this one, that lockfile is checked into version control (the same instinct as vendoring or a Go workspace's go.sum): a fresh checkout builds against the exact dependency graph that was tested, not "whatever satisfies the ranges today."

[profile.release] tunes the optimized build: opt-level = 3 is maximum optimization, and lto = "thin" enables a lighter-weight form of link-time optimization (inlining and dead-code elimination across the whole dependency graph, not just within one compilation unit) — cheaper to compile than full LTO, most of the runtime benefit.

Go contrast

Go infers a module's dependency graph from imports plus go.mod/go.sum; there's no per-target manifest section because a Go module usually builds one thing. Cargo separates what the crate is ([package], [[bin]]) from what it depends on ([dependencies]) from how to optimize it ([profile.*]) as distinct declarative sections in one file. Both ecosystems reject circular imports outright — Go at the package level, Rust at the crate and module level.

Crates vs. modules

A crate is a compilation unit — roughly Go's "module," a unit with its own dependency manifest. Inside a crate, modules (mod) are the namespace tree, closer to Go's packages, except Go infers packages from directory structure while Rust requires an explicit mod declaration to bring a file into the tree at all. lb/src/main.rs declares every other file in the crate as a module up front:

lb/src/main.rs
#[macro_use]
mod log;
mod backend;
mod balancer;
mod config;
mod health;
mod metrics;
mod net;
mod quic;
mod strategy;

Each mod backend; tells the compiler "load src/backend.rs as the backend module" (Rust also supports backend/mod.rs or backend/*.rs for modules with children; this crate is flat enough not to need that). #[macro_use] above mod log; is a gotcha covered in chapter 10 — module order matters when a module exports macros other modules use.

Once declared, items are reached with paths: crate::log::Level from anywhere in the crate, or a bare log::Level from a sibling module, or — after a use — just Level. main.rs's use block pulls the types it needs into scope by their short names:

lb/src/main.rs
use std::process::ExitCode;
use std::sync::Arc;

use tokio::sync::Notify;

use backend::Backend;
use balancer::Balancer;
use config::{Config, ParseOutcome};
use metrics::Metrics;
use strategy::Selector;

Everything is private by default: a function, struct field, or module is invisible outside its defining module unless marked pub. Backend's fields are a good example (chapter 6) — private fields force callers through accessor methods, which is how the crate guarantees every mutation of a backend's state goes through an atomic op.

Try it

In lb/, run cargo build and cargo build --release and compare target/debug/quixiot-lb and target/release/quixiot-lb with ls -lh (or time a cargo test run in each profile). Then run cargo doc --no-deps --open and browse the generated docs for the crate — notice that doc comments (//! at the top of each file, which you've now read in every source excerpt on this site) become the page prose.
