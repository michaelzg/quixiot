Chapter 03

Ownership, moves, borrowing

This is the chapter that makes Rust feel like a different language rather than "Go with semicolons and curly braces." Everything else — syntax, tooling, even most of the type system — you can pick up by pattern-matching against languages you know. Ownership you have to actually learn, because nothing in Go, Python, or Java prepares you for it. It's also the single biggest reason this crate has no unsafe, no data races, and no "who closes this socket?" bugs.

The three rules

  1. Every value has exactly one owner (one binding, one field, one Vec slot) responsible for it.
  2. Assigning a value, passing it to a function, or returning it moves ownership for any type that isn't Copy — the source binding becomes invalid, checked at compile time.
  3. When the owner goes out of scope, the value is dropped — deterministically, immediately, no garbage collector involved.

Rule 3 is RAII (resource acquisition is initialization), and it's the part that will feel most foreign coming from Go. A Session's upstream socket:

lb/src/balancer.rs — Session
struct Session {
    client: SocketAddr,
    backend: Arc<Backend>,
    upstream: Arc<UdpSocket>,
    last_seen_millis: AtomicI64,
    shutdown: Notify,
    closed: AtomicBool,
}

Nowhere in this crate is there an explicit "close this socket" call for upstream. The Session is held by an Arc (chapter 8) in the session table and by the return task; when the last of those references is dropped — the session is evicted or the client disconnects and everything holding an Arc<Session> finishes — the UdpSocket field's Drop implementation runs and the file descriptor closes. There is no path where someone forgets.

Go contrast

Go's equivalent is defer conn.Close() — it works, but it's a discipline you have to remember to apply at every call site that opens a resource, and code review is what catches the ones you forgot. The Go proxy's session close is explicit and centralized precisely because someone has to call it:

internal/proxy/proxy.go — (*session).close
func (s *session) close() error {
	var closeErr error
	s.closeOnce.Do(func() {
		close(s.done)
		if s.onClose != nil {
			s.onClose()
		}
		if err := s.upstreamConn.Close(); err != nil && !errors.Is(err, net.ErrClosed) {
			closeErr = err
		}
	})
	return closeErr
}

In Rust, cleanup is attached to the type itself via Drop, not to a call site that happens to be using it — you cannot forget to write the equivalent of defer, because there is nothing to write. This is also why Rust has no garbage collector: the compiler already knows, statically, the exact instant every value's last owner disappears, so it inserts the free (or close, or unlock) right there at compile time instead of discovering it's needed at runtime through GC. Chapter 8 puts this close side by side with this crate's exactly-once teardown in full.

Copy vs. move

Small, stack-only types (integers, bool, SocketAddr) implement Copy: assigning or passing them duplicates the bits, and the original stays valid — ordinary value semantics, exactly what you'd expect from Go. Backend::addr returns one by value with no ownership question at all:

lb/src/backend.rs — Backend::addr
pub fn addr(&self) -> SocketAddr {
    self.addr
}

Heap-backed types — String, Vec<T>, Arc<T> — are not Copy. Assigning one moves it: the old binding is gone, enforced at compile time, not just a style convention. When you do want an independent copy of one of these, you say so with .clone() — and for a heap type that's a real allocation and copy, not free. For an Arc, by contrast, .clone() is a refcount bump (chapter 8 covers exactly when the crate reaches for it, e.g. Arc::clone(&backend)). The point either way: in Rust, "this has a cost" and "you wrote .clone()" line up. Nothing copies silently behind your back.

Borrowing: &T and &mut T

Instead of moving or cloning, you can borrow a reference: &T is a shared, read-only borrow (you can have any number of these at once), &mut T is an exclusive, mutable borrow (at most one, and it excludes any &T borrows existing at the same time). The compiler enforces this — "aliasing XOR mutation" — statically, for every value, everywhere.

This sounds academic until you connect it to your actual experience: aliasing plus mutation is exactly the precondition for a data race (two threads, one writing) and for iterator invalidation (mutating a collection while iterating it) — two categories of bug that Go and C++ code review exist specifically to catch, and still miss. Rust's borrow checker is that code-review discipline, formalized and enforced by the compiler on every single build instead of by a human on the pull requests they happen to review carefully.

The hot forwarding path leans on shared borrows of buffer slices constantly — a slice &[u8] borrows a contiguous window of a buffer with zero copies:

lb/src/balancer.rs — Balancer::run
match session.upstream.try_send(&buf[..n]) {
    Ok(_) => {}
    Err(e) if e.kind() == ErrorKind::WouldBlock => self.metrics.drop_to_server(),
    Err(e) => self.handle_upstream_error(&session, e, "send to upstream"),
}
lb/src/balancer.rs — Balancer::return_loop
match self.listen.try_send_to(&buf[..n], session.client) {
    Ok(_) => {}
    Err(e) if e.kind() == ErrorKind::WouldBlock => {
        self.metrics.drop_to_client()
    }
    Err(e) => {
        warn!("send to client {} failed: {e}", session.client);
        break;
    }
}

&buf[..n] borrows the first n bytes of a datagram buffer that was read once and reused every iteration — no per-packet allocation, no copy, and the borrow checker guarantees nothing else mutates buf while that slice is alive. &str, mentioned last chapter, is exactly this idea specialized to UTF-8 text: a borrowed view into string data someone else owns.

War story: borrow at the call site

An early version of the idle-timeout flag handler read:

"--idle-timeout" => idle_timeout = Duration::from_secs(parse_u64(&value()?, flag)?),

which failed to compile with:

error[E0308]: mismatched types
  expected &str, found String
help: consider borrowing here: &flag

Diagnosis: parse_u64 takes flag: &str, but flag in scope is an owned String (it came from the argument iterator). Passing flag by value would move it — and this same flag is matched against in every other arm of the surrounding match, so it can't be given away. The compiler's own suggestion is the fix:

"--idle-timeout" => idle_timeout = Duration::from_secs(parse_u64(&value()?, &flag)?),

Deref coercion, while we're here: notice the function signature wants &str but call sites pass &flag where flag: String — that compiles because &String coerces to &str automatically (a String is always backed by valid UTF-8 with a &str view available). You will see this coercion constantly: functions in idiomatic Rust almost always take &str, never &String, precisely because callers holding either a String or a string literal can pass a borrow and it just works.

Lifetimes, briefly

A reference can't outlive the value it points to — the compiler checks this too, and the mechanism it uses is called a lifetime. Most of the time you never write one: elision rules infer them from a function's signature. When a method borrows self and returns a borrow, the returned reference is understood to borrow from self without any annotation:

lb/src/backend.rs — Backend::label
pub fn label(&self) -> &str {
    &self.label
}

&self.label's lifetime is tied to &self's automatically — the compiler won't let a caller hold onto that &str past the Backend's own lifetime. The one lifetime annotation you will see in this crate is &'static str, meaning "borrowed data that lives for the entire program" — true of string literals, which is exactly what Strategy::label returns:

lb/src/strategy.rs — Strategy::label
pub fn label(self) -> &'static str {
    match self {
        Strategy::RoundRobin => "round-robin",
        Strategy::LeastConnections => "least-conn",
        Strategy::Random => "random",
        Strategy::IpHash => "ip-hash",
    }
}

That's genuinely most of what you need to read lifetimes in this codebase. Writing more elaborate lifetime-generic code is a real skill, but it isn't load-bearing for understanding lb/ — elision handles essentially everything here.

Go contrast

Go's garbage collector and escape analysis solve a related problem differently: the compiler decides whether a value can live on the stack or must be heap-allocated based on whether a reference to it escapes the function, and the GC keeps anything still-reachable alive for as long as needed, full stop. You never annotate this and you never think about it — the cost is a runtime GC pass and less predictable latency. Rust's borrow checker proves the same “no reference outlives its data” property statically, at compile time, with zero runtime cost and zero GC pauses — the cost moves from runtime to your compile-time attention, which is the trade the rest of this chapter has been about.

Try it

In lb/src/config.rs, find the --health-interval arm and change parse_u64(&value()?, &flag)? to parse_u64(&value()?, flag)? (drop the borrow). Run cargo build and read the error — you should see the same shape as war story #2, but notice which later use of flag the compiler points at as the reason the move is illegal. Revert when you're done.
