Chapter 07

Vec, HashMap, iterators

Vec<T> and HashMap<K, V> are the same tools they are in any language; what's different is that iteration in Rust is built on a lazy adapter chain rather than an imperative loop with manual index bookkeeping.

The session table: Vec and HashMap in the hot path

The balancer's core state is a map from client address to session, guarded by a mutex (chapter 8 covers the locking discipline; this chapter is about the collection itself):

sessions: Mutex<HashMap<SocketAddr, Arc<Session>>>,

Lookup on the fast path is a plain HashMap::get, cloning the Arc out and dropping the lock immediately:

lb/src/balancer.rs — Balancer::get_or_create
async fn get_or_create(self: &Arc<Self>, client: SocketAddr) -> Option<Arc<Session>> {
    // Fast path: existing session under a short lock.
    if let Some(session) = self.sessions.lock().unwrap().get(&client).cloned() {
        return Some(session);
    }

and insertion on the slow path (after opening a new upstream socket) uses HashMap::insert, with a check for a session that raced ahead of this one:

lb/src/balancer.rs — Balancer::get_or_create
// Insert, guarding against a racing datagram that created the same
// session first: if we lost the race, drop ours and use theirs.
{
    let mut map = self.sessions.lock().unwrap();
    if let Some(existing) = map.get(&client).cloned() {
        drop(map);
        session.closed.store(true, Ordering::Relaxed); // ours never counted
        return Some(existing);
    }
    map.insert(client, Arc::clone(&session));
}

HashMap::retain is the filter-in-place tool: keep entries matching a predicate, drop the rest, without allocating a second map. The idle sweeper uses it to evict stale sessions while collecting the evictees for cleanup outside the lock:

lb/src/balancer.rs — Balancer::sweep_loop
async fn sweep_loop(self: Arc<Self>) {
    let mut ticker = tokio::time::interval(SWEEP_INTERVAL);
    loop {
        ticker.tick().await;
        let mut expired = Vec::new();
        {
            let mut map = self.sessions.lock().unwrap();
            map.retain(|_, s| {
                if s.idle_for() > self.idle_timeout {
                    expired.push(Arc::clone(s));
                    false
                } else {
                    true
                }
            });
        }

The closure passed to retain returns true to keep an entry, false to drop it — and as a side effect, pushes anything it's about to drop into expired first, so the teardown work (logging, waking the return task) can happen after the lock is released, not while the map is still held.

Go contrast

Go's proxy does the same sweep with a manual for range and explicit delete, because Go maps have no retain-style bulk filter:

internal/proxy/proxy.go — sweepLoop
p.sessionsMu.Lock()
for key, sess := range p.sessions {
	if sess.idleFor() > p.idleTimeout {
		delete(p.sessions, key)
		idle = append(idle, sess)
	}
}
p.sessionsMu.Unlock()

Same idea, more manual bookkeeping: build a slice by hand while deleting from the map you're iterating (safe in Go specifically for deletion during range, but not for insertion). Rust's retain expresses the same filter-and-collect operation as one named method instead of an open-coded loop.

Iterator adapters are lazy until collect

Methods like .iter(), .filter(), and .map() build up a chain of work without doing anything — nothing executes until something actually consumes the iterator (.collect(), a for loop, .sum(), and so on). Selector::select filters backends down to the healthy subset this way:

let healthy: Vec<&Arc<Backend>> = backends.iter().filter(|b| b.is_healthy()).collect();

and least-connections selection chains .iter() into .min_by_key():

lb/src/strategy.rs — Selector::select
Strategy::LeastConnections => healthy
    .iter()
    .min_by_key(|b| b.active_sessions())
    .copied()
    .expect("healthy is non-empty"),

main.rs builds the backend pool itself with a .iter().map().collect() chain, turning a Vec<SocketAddr> from config into a Vec<Arc<Backend>>:

lb/src/main.rs — serve
let backends: Arc<Vec<Arc<Backend>>> = Arc::new(
    cfg.backends
        .iter()
        .map(|addr| Arc::new(Backend::new(*addr)))
        .collect(),
);

and backend-list parsing runs a .split(',') iterator through a for loop with per-token trimming and validation — from chapter 2:

lb/src/config.rs — parse_backends
for token in raw.split(',') {
    let token = token.trim();
    if token.is_empty() {
        continue;
    }
    out.push(parse_addr(token)?);
}

Turbofish and collect's target-type inference

.collect() is generic over its output type — it needs to be told what to build, either via the binding's type annotation or via the turbofish syntax ::<Type> at the call site. This crate consistently uses the first style, annotating the binding:

let backend_list: Vec<String> = cfg.backends.iter().map(|b| b.to_string()).collect();

The alternative — not used in this crate, shown here purely as a syntax reference — would push the same type information onto the call itself:

syntax note — not from this crate
let backend_list = cfg.backends.iter().map(|b| b.to_string()).collect::<Vec<_>>();

Both compile to the same code; which one reads better depends on whether the surrounding line already makes the target type obvious. This codebase prefers annotating the binding, which keeps the chain itself uncluttered.

Building strings without per-line allocation

The Prometheus text renderer builds one big string incrementally instead of formatting and concatenating many small ones. String::with_capacity pre-allocates, and write!/writeln! (via std::fmt::Write, imported explicitly) append formatted text in place:

use std::fmt::Write as _;
let mut out = String::with_capacity(2048);
lb/src/metrics.rs — metric
fn metric(
    out: &mut String,
    name: &str,
    kind: &str,
    help: &str,
    samples: &[(&[(&str, &str)], f64)],
) {
    let _ = writeln!(out, "# HELP {name} {help}");
    let _ = writeln!(out, "# TYPE {name} {kind}");
    for (labels, value) in samples {
        write_sample(out, name, labels, *value);
    }
}

write!(out, ...) is the string-building sibling of println! — same format-string syntax, different destination. Because out already has capacity reserved, appending each metric line only occasionally triggers a reallocation, instead of every single format!() call in a naive "concatenate many small strings" version allocating its own throwaway String.

Try it

In lb/src/metrics.rs, change String::with_capacity(2048) to String::new() and run cargo test — the tests still pass, because capacity is a performance hint, not correctness. Then read render()'s full body end to end and count how many separate metric families it emits with this one growing String, versus how many separate HTTP response allocations that would have been with one write call per metric.
