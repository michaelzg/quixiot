Chapter 08

Fearless concurrency

This is the chapter this whole crate exists to demonstrate. The claim — that data races become compile errors instead of code-review catches — sounds like marketing until you see it enforced on a type you actually understand. Backend is that type.

Send and Sync are derived, not written

Send (safe to move to another thread) and Sync (safe to share by reference across threads) are traits, but you never write impl Send for Backend. The compiler derives them automatically: a type is Send/Sync if and only if every one of its fields is. Recall Backend's fields from chapter 6:

lb/src/backend.rs — Backend
pub struct Backend {
    addr: SocketAddr,
    /// Label used in logs and metrics; the address string is stable and unique.
    label: String,
    healthy: AtomicBool,
    active_sessions: AtomicI64,
    selected_total: AtomicU64,
    /// Consecutive active-probe failures; reset to 0 on any success.
    health_failures: AtomicU64,
}

Every field is an atomic type, and every atomic type is Sync by construction (that's the entire point of atomics: they define what happens when multiple threads touch them concurrently). Because every field qualifies, Backend is Sync automatically — which is what makes &Backend (and therefore Arc<Backend>) safe to hand to the receive loop, every session's return task, and the health checker simultaneously. Swap one field for a plain, non-atomic i64 and Backend silently stops being Sync — and every place that shares it across an await or a spawned task stops compiling, with the compiler pointing at exactly the field that broke it. That's the mechanism behind the "compile error, not a code review catch" claim: it isn't a lint, it's a consequence of the type system that falls out for free once every field is atomic.

Arc<T>: shared ownership across tasks

Arc<T> (atomically reference-counted) is a pointer to heap data with a shared-ownership refcount, safe to clone across threads — clone bumps the count (cheap, lock-free), drop decrements it, and the data is freed when the count hits zero. It's the multi-owner escape hatch from chapter 3's "exactly one owner" rule, used precisely where multiple concurrent tasks legitimately need the same data to outlive any one of them. This crate reaches for it everywhere ownership needs to be shared: individual backends (Arc<Backend>), the whole pool (Arc<Vec<Arc<Backend>>>), each session (Arc<Session>), the metrics block (Arc<Metrics>), and the balancer itself:

lb/src/main.rs — serve
let backends: Arc<Vec<Arc<Backend>>> = Arc::new(
    cfg.backends
        .iter()
        .map(|addr| Arc::new(Backend::new(*addr)))
        .collect(),
);

and every method that needs to hand a copy of itself into a spawned task takes self: Arc<Self> instead of &self:

pub async fn run(self: Arc<Self>, shutdown: Arc<Notify>) {
async fn get_or_create(self: &Arc<Self>, client: SocketAddr) -> Option<Arc<Session>> {
async fn return_loop(self: Arc<Self>, session: Arc<Session>) {
async fn sweep_loop(self: Arc<Self>) {

That's Balancer::run, get_or_create, return_loop, and sweep_loop — four different methods, all taking the balancer itself as an Arc because all four need to hand a live, still-owned handle to a task that will outlive the current call. tokio::spawn requires its future to be 'static (own everything it touches, borrow nothing from the caller's stack), and Arc::clone is exactly how you satisfy that without literally copying the balancer's state.

Mutex<T> wraps the data, not a code section

Go's sync.Mutex guards a critical section of code — nothing stops you from touching the protected data outside the lock, except discipline. std::sync::Mutex<T> wraps the data itself: there is no way to obtain a &HashMap from inside the session table without going through .lock() first, and the returned guard borrows the mutex for exactly as long as you hold it. The type system, not convention, is what prevents an unguarded access.

That guarantee comes with a new failure mode to manage by hand: holding a lock across an .await point blocks every other task waiting on that mutex for as long as the await takes — potentially a full network round trip. get_or_create's own comment states the rule it follows:

lb/src/balancer.rs — Balancer::get_or_create
// Choose a backend and open the upstream socket *before* taking the lock
// again, so the await points don't hold the mutex across .await.

The pattern in practice: select a backend and open the upstream socket (both of which may .await) before taking the lock; then take the lock only for the plain, synchronous HashMap read or insert, and let the guard drop immediately. The Arc<Session> gets cloned out from behind the lock, and every subsequent line of code operates on that owned clone — never on a reference still borrowed from the guard.

Atomics and memory ordering, briefly

Atomic types (AtomicBool, AtomicI64, AtomicU64, ...) give lock-free, thread-safe reads and writes of a single value via CPU-level atomic instructions. The hot path records every packet with one fetch_add, no lock anywhere in sight:

lb/src/metrics.rs — Metrics::add_to_server
pub fn add_to_server(&self, bytes: usize) {
    self.packets_to_server.fetch_add(1, Ordering::Relaxed);
    self.bytes_to_server
        .fetch_add(bytes as u64, Ordering::Relaxed);
}
lb/src/backend.rs — inc_sessions / dec_sessions
pub fn inc_sessions(&self) {
    self.active_sessions.fetch_add(1, Ordering::Relaxed);
}

pub fn dec_sessions(&self) {
    self.active_sessions.fetch_sub(1, Ordering::Relaxed);
}

Every one of those uses Ordering::Relaxed — and almost everything in this crate does. Keep the mental model to two paragraphs: Relaxed means "this operation is atomic (no torn reads, no lost updates) but carries no promise about the ordering of any other memory access around it" — correct for independent counters where you only care that increments aren't lost, not about what happened concurrently elsewhere. Stronger orderings (Acquire, Release, AcqRel, SeqCst) additionally synchronize memory visibility between threads around that specific operation — use them when one atomic's value is standing in for "is it safe to look at other data now."

Exactly one operation in this crate uses AcqRel instead of Relaxed, and it's the one place that decision actually matters, covered next.

The flagship comparison: exactly-once teardown

Every session needs to be torn down exactly once, no matter which of several concurrent paths discovers it should close first — the receive loop can decide a client is being rejected, the return task can see the upstream socket error, and the idle sweeper can independently decide the session is stale, all around the same moment. Go and Rust solve "who wins the race to clean this up" with completely different primitives.

The Go proxy answers it with sync.Once plus a channel close:

closeOnce sync.Once
done      chan struct{}
internal/proxy/proxy.go — (*session).close
func (s *session) close() error {
	var closeErr error
	s.closeOnce.Do(func() {
		close(s.done)
		if s.onClose != nil {
			s.onClose()
		}
		if err := s.upstreamConn.Close(); err != nil && !errors.Is(err, net.ErrClosed) {
			closeErr = err
		}
	})
	return closeErr
}

sync.Once.Do guarantees its function argument runs exactly once no matter how many goroutines call close() concurrently — the runtime handles the mutual exclusion internally. close(s.done) is the actual signal: closing an already-closed channel panics, so sync.Once is also what protects against a double-close panic here, not just against redundant work.

This crate answers the identical problem with one boolean and one compare-and-swap, no mutex and no runtime-managed primitive at all:

closed: AtomicBool,
lb/src/balancer.rs — Balancer::finish
fn finish(&self, session: &Arc<Session>) {
    if session.closed.swap(true, Ordering::AcqRel) {
        return;
    }
    session.shutdown.notify_one();
    session.backend.dec_sessions();
    self.metrics.session_closed();
}

Go — sync.Once + channel close

State: closeOnce sync.Once field (module-level object, opaque internal state) plus a closed chan struct{} as the actual signal.

Winning caller runs the closure inside Do; losers block until the closure finishes, then return immediately — sync.Once makes that blocking-until-done guarantee for you.

Rust — AtomicBool CAS

State: one AtomicBool field, no separate runtime object.

swap(true, AcqRel) atomically sets closed to true and returns what it was a moment before. If that was already true, this caller lost the race and returns immediately — no blocking, no waiting for the winner to finish.

This is why finish is the one place in the crate that reaches for Ordering::AcqRel instead of Relaxed: the swap on closed isn't just a counter, it's a gate deciding whether this call proceeds to touch session.backend and self.metrics at all. AcqRel (acquire-release) ensures that whichever caller wins the swap has a synchronized view of everything written before any prior attempt, and that its own writes (decrementing the backend's session count, closing the metrics gauge) become visible to anyone who checks closed afterward. Notify::notify_one then wakes the return task — covered fully in chapter 9 — which is this crate's equivalent of the channel close signaling the same shutdown.

Same guarantee, both languages: whoever calls the teardown function first does the work, everyone else is a safe, cheap no-op. Go leans on a runtime-provided synchronization object built for exactly this pattern; Rust expresses the identical guarantee as one atomic read-modify-write instruction with no separate object needed at all — ownership plus one boolean is the whole mechanism.

Try it

In lb/src/balancer.rs, change finish's session.closed.swap(true, Ordering::AcqRel) to use Ordering::Relaxed instead, and run cargo test in lb/. The suite will very likely still pass — this is the sharp edge of memory-ordering bugs: they're usually invisible until timing conditions on a different platform or under load expose the missing synchronization. Read the comment above finish again, then revert. Being able to explain why AcqRel is the right choice here, even though a weaker ordering often “works,” is the actual exercise.
