Chapter 05

Result and the ? operator

You already think in errors-as-values from Go — this chapter is mostly about the specific vocabulary Rust uses for the same idea, plus the ? operator, which is the one piece with no direct Go equivalent.

Result<T, E>

Result<T, E> is Option's sibling: Ok(T) or Err(E), a real type, checked exhaustively like any other enum. Where Go returns (value, error) as two separate values and trusts you to check err != nil before touching value, Rust's version is one value that can only be in one state at a time — there's no way to hold a meaningless zero-valued T next to a non-nil error, because there's no T at all in the Err case.

?: tracing one real chain

The ? operator is early-return propagation: on an Err, it returns that Err from the enclosing function immediately; on Ok, it unwraps to the inner value and execution continues. It's the Rust equivalent of Go's if err != nil { return err }, except it's one character and the compiler enforces that you can't accidentally use the value without having handled the error path.

Follow one real path end to end. It starts in main:

lb/src/main.rs — main
let cfg = match config::parse(std::env::args().skip(1)) {
    Ok(ParseOutcome::Run(cfg)) => cfg,
    Ok(ParseOutcome::Help) => {
        print!("{}", config::usage());
        return ExitCode::SUCCESS;
    }
    Err(msg) => {
        eprintln!("quixiot-lb: {msg}");
        return ExitCode::FAILURE;
    }
};

config::parse returns Result<ParseOutcome, String>. Inside it, flags like --listen call parse_addr(&value()?)? — two ?s in one expression: the first propagates a missing-value error from the value() closure (chapter 2), the second propagates a resolution failure from parse_addr itself:

lb/src/config.rs — parse_addr
fn parse_addr(s: &str) -> Result<SocketAddr, String> {
    s.to_socket_addrs()
        .map_err(|e| format!("bad address {s:?}: {e}"))?
        .next()
        .ok_or_else(|| format!("address {s:?} resolved to nothing"))
}

If either fails, the String error bubbles all the way up through config::parse's return, without any of the intermediate call sites writing a single if err != nil check. It surfaces in main's match above as Err(msg), gets printed with eprintln!, and main returns ExitCode::FAILURE — a typed alternative to os.Exit(1) that still lets destructors run on the way out, since it's a normal return rather than a process-terminating call.

Go contrast

The same shape, in Go, is cmd/server/main.go's split between main and run:

cmd/server/main.go
func main() {
	if err := run(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

run returns a plain error that every fallible step inside it propagates with if err != nil { return err } or a wrapped fmt.Errorf("...: %w", err); main is the one place that decides what to do with a top-level failure (print it, exit 1). The Rust version is structurally the same instinct — a thin main, a fallible core, explicit propagation — with ? replacing the repeated if err != nil boilerplate at every call site.

Error types: pragmatism over hierarchy

This crate uses a plain String for CLI/config errors — pragmatic for a small tool where every error is ultimately just a message printed to stderr, and not worth a custom error enum. Where a function is doing real I/O, it uses std::io::Error instead, because that's the type the standard library itself produces and callers may want to inspect its ErrorKind (chapter 9 uses exactly that to distinguish "connection refused" from other failures):

async fn dial_upstream(&self, backend: &Backend) -> std::io::Result<UdpSocket> {
pub fn bind_udp(addr: SocketAddr, buf_bytes: usize) -> std::io::Result<(UdpSocket, usize)> {

As a codebase grows past "every error is a string," the common next step is Box<dyn std::error::Error> (any error type, boxed, at some cost to matching on specific variants) or a hand-written enum with a crate like thiserror generating the boilerplate (each error case as its own enum variant, structured and matchable). Neither is warranted here — worth knowing the scaling path exists without reaching for it prematurely.

unwrap and expect: policy, not prohibition

.unwrap() and .expect("message") convert a Result/Option into its inner value or panic — an unrecoverable, unwinding failure, not a Result the caller can handle. They're fine in two situations: tests (a failing precondition should abort that test loudly), and cases the type system can't see are infallible but you can prove by inspection. The crate's default listen address is a literal you control:

lb/src/config.rs — Config::default_listen
impl Config {
    fn default_listen() -> SocketAddr {
        "127.0.0.1:4450".parse().unwrap()
    }

"127.0.0.1:4450" is a hardcoded, valid address string; parsing it can never actually fail, so .unwrap() just asserts that fact rather than threading a Result through a function that has no real failure mode. Same reasoning in Selector::select's least-connections arm:

.expect("healthy is non-empty"),

the caller already checked healthy is non-empty two lines earlier, so .expect(...) documents why this can't fail rather than silently hoping. Outside of proven-infallible cases and tests, reaching for unwrap instead of propagating with ? is a smell — it turns a recoverable error into a crash.

Mutex poisoning

The session table is guarded by a Mutex, and every lock site in this crate calls .lock().unwrap():

if let Some(session) = self.sessions.lock().unwrap().get(&client).cloned() {

Mutex::lock() returns a Result, not the guard directly, because if a thread panics while holding the lock, the mutex becomes “poisoned” and every subsequent .lock() returns Err rather than silently handing out a guard over data that might be in a half-mutated, inconsistent state. .unwrap() here is a deliberate policy: this crate treats poisoning as unrecoverable (a panic while the map is locked means a bug, and the process should go down loudly rather than limp on with possibly-corrupt session state) — not a case where ? should propagate a soft error.

Panics vs. Results

Use a Result when the caller has a reasonable way to recover (a bad CLI flag, a socket that failed to open once). Panic when continuing would mean operating on data you've already proven is broken (a poisoned mutex above), or when something is a programmer error rather than a runtime condition (an index out of bounds, an assertion in a test). The line matches your Go instincts about when to return an error versus when to legitimately let a goroutine crash — Rust just gives the "recoverable failure" path a real type instead of an interface value that's sometimes nil.

Try it

In lb/src/config.rs, change Config::default_listen's literal from "127.0.0.1:4450" to something unparseable, like "not-an-address", and run cargo test. Watch .unwrap() stop being infallible and turn into a real panic — this is exactly the risk the crate is accepting every time it reaches for unwrap instead of ?. Revert the change afterward.
