Chapter 06

Structs, impl, traits, derive

struct plus impl is Rust's answer to "define a type and its behavior," and trait is its answer to "interface" — both will feel immediately familiar, with a few sharp differences worth calling out precisely.

Struct + impl: Backend as a tour

A struct is just fields; behavior lives in one or more separate impl blocks. Backend's fields are private by default (no pub):

lb/src/backend.rs — Backend
pub struct Backend {
    addr: SocketAddr,
    /// Label used in logs and metrics; the address string is stable and unique.
    label: String,
    healthy: AtomicBool,
    active_sessions: AtomicI64,
    selected_total: AtomicU64,
    /// Consecutive active-probe failures; reset to 0 on any success.
    health_failures: AtomicU64,
}

Privacy means nothing outside backend.rs can construct a Backend with an inconsistent state or mutate healthy directly — every read and write goes through a method, and every one of those methods goes through an atomic operation (chapter 8). This is Rust's version of "make the zero value useless, force construction through a constructor" — enforced by the compiler, not just convention.

Methods take self in one of three forms, and the crate uses only the first two: &self (shared borrow — can read, can't mutate directly), &mut self (exclusive borrow — can mutate), or plain self (takes ownership, consuming the value — used for builder-style APIs that transform and return a new value, rare in this crate). Every Backend method takes &self, even the ones that update counters:

lb/src/backend.rs — mark_up / mark_down
/// Mark healthy and clear the failure streak. Logs only on the down→up edge
/// so steady-state probing stays quiet.
pub fn mark_up(&self) {
    self.health_failures.store(0, Ordering::Relaxed);
    if !self.healthy.swap(true, Ordering::Relaxed) {
        info!("backend {} recovered -> healthy", self.label);
    }
}

/// Mark unhealthy immediately. Logs only on the up→down edge.
pub fn mark_down(&self) {
    if self.healthy.swap(false, Ordering::Relaxed) {
        warn!("backend {} marked unhealthy", self.label);
    }
}

mark_up and mark_down clearly mutate state, yet neither needs &mut self. That's only possible because every field is an atomic type with interior mutability — the ability to mutate through a shared reference, safely, via the hardware's atomic instructions instead of the borrow checker's exclusivity rule. Chapter 8 is entirely about why that's sound and why it's the reason Backend can be shared across every task touching it at once.

Associated functions vs. methods

A function inside an impl block that doesn't take self is an associated function — called via Type::function(...) rather than value.method(...). Constructors are the common case:

lb/src/backend.rs — Backend::new
impl Backend {
    pub fn new(addr: SocketAddr) -> Self {
        Backend {
            addr,
            label: addr.to_string(),
            // Optimistic: assume up until a probe or a live error says otherwise.
            healthy: AtomicBool::new(true),
            active_sessions: AtomicI64::new(0),
            selected_total: AtomicU64::new(0),
            health_failures: AtomicU64::new(0),
        }
    }

Backend::new(addr) is how every backend gets created; there's no implicit/default construction the way a Go struct literal with omitted fields silently zero-values everything. Self is shorthand for "the type this impl block is for" — useful in generic or heavily-nested code; Balancer::new uses it in its return type:

lb/src/balancer.rs — Balancer::new
impl Balancer {
    pub fn new(
        listen: UdpSocket,
        backends: Arc<Vec<Arc<Backend>>>,
        selector: Selector,
        metrics: Arc<Metrics>,
        idle_timeout: Duration,
    ) -> Arc<Self> {
        Arc::new(Balancer {
            listen: Arc::new(listen),
            backends,
            selector,
            metrics,
            idle_timeout,
            sessions: Mutex::new(HashMap::new()),
            pool_down_warned: AtomicBool::new(false),
        })
    }

Returning Arc<Self> instead of a bare Balancer is a deliberate API choice, previewed here and explained fully in chapter 8: nearly every method on Balancer needs to be callable from a spawned task, which means the balancer itself needs to live behind a reference-counted pointer from the moment it's constructed.

Traits: compile-time interfaces

A trait declares behavior a type can implement, much like a Go interface — but where Go interfaces are satisfied structurally (any type with the right methods qualifies, implicitly), Rust impl Trait for Type is explicit, and resolution happens at compile time by default (static dispatch, monomorphized per concrete type) rather than through a runtime interface table. You'll recognize traits by name even before writing one: Default (a type-defined "zero value" constructor), and the formatting traits Display (user-facing {} formatting) and Debug (developer-facing {:?} formatting). Metrics derives Default so every atomic counter starts at zero without hand-writing a constructor:

lb/src/metrics.rs — Metrics
#[derive(Default)]
pub struct Metrics {
    pub packets_to_server: AtomicU64,
    pub packets_to_client: AtomicU64,
    pub bytes_to_server: AtomicU64,
    pub bytes_to_client: AtomicU64,
    pub dropped_to_server: AtomicU64,
    pub dropped_to_client: AtomicU64,
    pub sessions_active: AtomicI64,
    pub sessions_total: AtomicU64,
    pub sessions_rejected: AtomicU64,
    pub quic_initials: AtomicU64,
}
let metrics = Arc::new(Metrics::default());

#[derive(...)]: generating trait impls

#[derive(Trait)] asks the compiler to generate a mechanical implementation — no hand-written boilerplate, no risk of the implementation drifting from the fields it should cover. This crate reaches for it constantly:

#[derive(Clone, Debug)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]

Clone gives you .clone(); Copy (only valid for types that are safe to bitwise-duplicate) switches a type from move to copy semantics (chapter 3); Debug enables {:?} formatting for logging and test assertions; PartialEq/Eq enable ==; PartialOrd/Ord (on Level) enable </> comparisons — which is exactly how log::enabled compares a message's level against the configured minimum.

War story: trait bounds in std APIs

An early config test called .unwrap_err() on a parse result whose Ok type was ParseOutcome:

lb/src/config.rs — requires_backends
#[test]
fn requires_backends() {
    let err = parse(args(&[])).unwrap_err();
    assert!(err.contains("--backends"));

and the build failed with:

error[E0277]: `ParseOutcome` doesn't implement `Debug`
required by a bound in `Result::<T, E>::unwrap_err`

Diagnosis: Result::unwrap_err's signature bounds T: Debug — if the value turns out to actually be Ok, the panic message needs to print it, which requires a Debug impl on the Ok type. ParseOutcome didn't have one yet. Fix: one derive:

lb/src/config.rs — ParseOutcome
#[derive(Debug)]
pub enum ParseOutcome {
    Run(Config),
    Help,
}

Lesson: standard library APIs constrain their generic parameters with trait bounds, and a missing bound is a compile error naming the exact trait you're missing and the exact API that requires it — not a vague runtime failure. Once you learn to read E0277, “add the derive it's asking for” becomes a reflex.

Generics and bounds

config::parse doesn't take a concrete Vec<String>; it's generic over anything iterable:

pub fn parse<I: IntoIterator<Item = String>>(args: I) -> Result<ParseOutcome, String> {

I: IntoIterator<Item = String> is a trait bound: "any type I, as long as it can produce an iterator of Strings." That accepts Vec<String> (used by every test in this file), env::args().skip(1) (used by main), or any other iterable — without parse ever committing to one concrete collection type. The compiler generates a separate, fully specialized version of parse for each concrete type it's actually called with (monomorphization), so this generality costs nothing at runtime — no boxing, no dynamic dispatch, unlike a Go function taking an interface parameter, which does incur an interface-value indirection.

One more preview, expanded fully in chapter 8: Send and Sync are traits too, but you never write impl Send for Backend — the compiler auto-derives them based on whether every field is itself Send/Sync. That's what makes a type like Backend safe to share across tasks, and it's checked the same mechanical way every other trait bound is: at compile time, exhaustively.

Try it

Add a #[derive(Debug)] line above the Backend struct in lb/src/backend.rs, then in a scratch #[test] (or in strategy.rs's existing tests, which already construct backends), try printing one with println!("{:?}", backend). Then remove the derive again and re-run — read the E0277 the compiler gives you and notice it's the same shape as war story #3.
