Chapter 12

Rust vs Go retrospective

You've now read every major corner of a real, working Rust service, mapped directly against a Go codebase that solves the identical problem. This chapter closes the loop: one table, an honest scorecard in both directions, and where to go from here.

Reading this table honestly

Treat every row as “closest analogue,” not “identical mechanism.” Notify plus an mpsc channel covers what a bare Go channel does, but they're two different Rust primitives reached for in different situations, not one drop-in replacement. Trait dispatch is static by default in Rust and dynamic by default for a Go interface value — a real behavioral difference, not just a spelling one. The table is a map to help you orient, not a claim that the two languages are secretly the same language.

Where Go was honestly simpler

  • No readiness priming needed. War story #4 (chapter 9) was entirely a consequence of Rust's non-blocking I/O making reactor readiness state observable. Go's netpoller hides exactly this layer — conn.Write() blocks the goroutine transparently until the OS says the socket is writable, so a fresh socket's first write can never surprise you with a spurious not-ready result. That whole category of bug simply cannot happen in the Go proxy.
  • GC removes an entire axis of thought. Nothing in the Go codebase needed a moment's consideration of who owns a value or how long a reference can live — the garbage collector made that a non-question. Chapter 3's ownership rules buy real guarantees, but they are a genuine, continuous tax on how you write code, especially early on.
  • Faster compile loop. Go's compiler is famously fast; Rust's borrow checker, trait resolution, and (for release builds) LTO make the edit-compile-test cycle noticeably slower, particularly for cargo build --release. This crate is small enough that it barely matters; it matters a great deal more at scale.

What Rust bought this crate

  • Data-race prevention at compile time. Chapter 8's whole premise: Backend is safe to share across every task touching it because the compiler proved it, not because a reviewer checked it carefully.
  • Exhaustive matching as a standing guarantee. Chapter 4: add a Strategy variant and the compiler finds every site that needs updating, forever, automatically — no grep, no hoping you remembered everywhere.
  • No-null, no-exception control flow. Option and Result (chapters 4 and 5) make "this might not exist" and "this might fail" part of a function's type, not an implicit possibility a caller has to remember to guard against.

Keep this scorecard honest rather than one-sided: both languages made deliberate, defensible trade-offs, and this repo's own choice to implement the same load balancer twice — once in each — is precisely so those trade-offs are visible side by side instead of argued about in the abstract.

Where to go next

Reading this site is a start, not a substitute for writing Rust. Three habits worth building:

  • Work through The Rust Book (further reading, not loaded by this site) end to end — it covers everything here in more depth, plus trait objects, Rc/RefCell, and other topics this guide deliberately skipped as not load-bearing for reading lb/.
  • Do a pass of Rustlings — small, broken programs you fix one compiler error at a time. It's the fastest way to get fluent in reading the exact kind of error messages chapters 2, 3, and 6 walked through.
  • Build the habit of reading std docs for Option, Result, and Iterator's method lists start to finish at least once. Idiomatic Rust leans heavily on combinators (chapter 4's ok_or_else/map_err, chapter 7's iterator chains); knowing what's available changes how you write every function afterward.

Concrete exercises against this crate

All four touch real files you've now read in full. Do them in a scratch branch off this repo, and lean on cargo test as you go — and on the exhaustiveness checking from chapter 4, which will find most of the call sites for you.

  1. Add a weighted strategy (--backends addr@3,addr@1 — higher weight means proportionally more new sessions). Touches config.rs's backend-list parsing, a new Strategy::Weighted variant in strategy.rs, and new tests alongside the existing strategy tests.
  2. Add a quixiot_lb_backend_health_transitions_total metric counting up→down and down→up edges per backend. Touches backend.rs's mark_up/mark_down (chapter 6) and metrics.rs's render (chapter 7).
  3. Make the idle sweep interval configurable (currently the SWEEP_INTERVAL constant in balancer.rs). Config plumbing end to end: a new flag in config.rs, a new Config field, threaded into Balancer::new.
  4. Harder: per-session byte counters, exposed with a /metrics label per backend. Touches the Session struct (chapter 3), the forwarding loops in balancer.rs (chapter 9), and the labeled-series rendering pattern already used for quixiot_lb_backend_sessions_active in metrics.rs (chapter 7).
Try it

Pick exercise 1, the weighted strategy, and actually build it. Start in lb/src/strategy.rs: add Weighted to the Strategy enum (chapter 4's exhaustiveness check will now show you every match arm that needs updating), extend Selector to hold per-backend weights, and write a deterministic test in the same style as round_robin_cycles (chapter 11) asserting the distribution matches the configured weights over a fixed number of selections. Then wire --backends addr@3,addr@1 parsing into config.rs::parse_backends (chapter 2's for-loop-over-split pattern, extended to split on @ too). Run cargo test the whole way — this exercise alone touches ownership, enums, generics, iterators, and testing, which is exactly why it's the first one.
